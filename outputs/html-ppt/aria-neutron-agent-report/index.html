Aria Firewall · v0.9-neutron-agent01 / 22

开场先讲结论。这次不是做一个新的控制平台，也不是把 v0.10 的 controller 搬进来。我们要做的是 OpenStack 的 Neutron Agent Mode。

也就是说，OpenStack 用户还是通过 Neutron、Horizon、Terraform 这些入口配置网络；Aria 只在 compute node 上接管节点侧 datapath 能力。

第一阶段的边界非常重要：目标环境固定 OVS，Aria 不替代 L2 连接路径，只新增 ACL enhancement 和 QoS 两个功能模块。

开发汇报 · 结论页02 / 22

这一页是给管理层和开发团队对齐用的。我们不再讨论自研控制面是否替代 Neutron，因为在 OpenStack 里这个方向不划算。

Neutron 已经承担了租户、端口、网络、QoS、绑定、RBAC、agent heartbeat。我们应该做的是把 Aria 接进 Neutron 体系，成为一个本机 agent。

开发顺序也要收敛：先做 ACL/QoS 两条纵向闭环，再谈其它能力；先把失败边界、WAL、Netlink、pinned maps 打牢，再进入生产 smoke。

架构 · 两容器边界05 / 22

目标架构很简单。上游仍然是 OpenStack 用户通过 Neutron 配置对象。Neutron server 继续掌握 port、QoS、binding 和多租户关系；当前阶段不把 Security Group 投影给 Aria。

compute node 上新增一个 Python 的 neutron-aria-agent，它只负责读 Neutron、本机投影、生成 snapshot，然后通过 Unix socket 调用本机 datapath。

Rust 侧叫 aria-datapath，这是角色名和容器名，里面仍然跑现有 aria-agent 二进制。两个容器之间只通过 /run/aria/aria-agent.sock 通信。

component boundaries

三个边界必须守住：Neutron 管语义，Python 管投影，Rust 管执行。

Neutron

  • source of truth
  • project / RBAC / shared network
  • port binding / QoS
  • agent heartbeat

neutron-aria-agent

  • Python 编写
  • 只处理本 host ports
  • 翻译 ACL enhancement / QoS
  • full resync + event merge

aria-datapath

  • Rust runtime
  • 不访问 Neutron DB
  • eBPF attach/map apply
  • WAL / Netlink / pinned maps
Rust 侧不解释 Neutron 内部语义；Python 侧不直接操作 eBPF map。
职责边界06 / 22

这页是后面代码 review 的基本边界。Neutron 负责用户语义，Python adapter 负责投影，Rust datapath 负责执行。

Rust 不应该知道 Neutron DB 内部结构，也不消费 Neutron RPC；否则后面版本兼容会很痛苦。

Python 也不应该直接写 eBPF map，它只生成声明式 snapshot。这样失败恢复、幂等、WAL 和 status 才能统一。

功能范围 · 两个 feature domain07 / 22

OpenStack 模式第一阶段对外只暴露两个功能域：ACL enhancement 和 QoS。其它已有能力不是删除，而是不进入 Neutron agent 暴露面。

同时有 Group、Conntrack、Monitoring、WAL、Netlink 和 pinned maps 这些支撑能力必须保留。这些不是租户功能。

ACL 不是当前阶段的业务连通性硬门槛；ACL 或 conntrack 未 ready 时，Aria 必须 degraded/bypass，原 OVS 转发不能中断。

acl implementation principle

ACL 只做显式 enhancement：Neutron 负责输入，Aria 负责本机执行。

01 intentoperator-admin 通过 Neutron tag 指向显式 ACL policy。
02 mappingPython 读取只读 mapping，不新增 tenant northbound。
03 scope按 port owner project 编译 scoped group/address-set。
04 snapshot输出 ACL domain，不包含 Security Group projection。
05 datapathRust apply groups → conntrack → ACL maps。
06 statusready/degraded/not_requested 都带 effective_action。

语义边界

不消费 Neutron Security Group、remote group、port security 或 allowed address pairs；跨 project 访问必须来自显式 ACL enhancement policy。

失败边界

ACL 未配置就是 bypass；配置错误或 apply 失败是 degraded + bypass，不形成默认拒绝，也不影响原 OVS connectivity。

ACL 原理 · 显式增强08 / 22

ACL 的关键不是把 Neutron Security Group 复制一遍，而是只做显式 enhancement。输入来自 operator-admin 管理的 Neutron tag 和本机只读 mapping。

Python translator 负责把 port、project、ACL group 和 CIDR 编译成 scoped address-set 和 per-port ACL policy。Rust 侧只执行 snapshot，不重新解释 Neutron RBAC。

失败语义必须保守：未配置是 bypass，配置失败是 degraded + bypass，不能因为 Aria ACL 未 ready 就让原 OVS 转发中断。

qos implementation principle

QoS 以 per-port effective policy 为准，失败只降级 QoS domain。

Translator 计算规则

1

先收集 Neutron port-level、network-level 和 shared QoS policy。

2

按 port-level > network-level > shared default 生成 effective QoS。

3

第一版只把 bandwidth limit 进入可执行路径。

4

minimum bandwidth、DSCP 等不支持项进入 unsupported/degraded status。

Datapath 执行规则

✓

Rust 按 port policy 写入 QoS map / qdisc 相关状态。

✓

egress shaping 可观察；ingress policing 降级必须明确上报。

✓

删除 QoS policy 后必须清理 token bucket 和对应状态。

✓

QoS degraded 不影响 ACL ready，也不影响原 OVS 转发。

QoS 是独立 feature domain：policy 绑定、运行状态和失败原因都按 port 可观测。
QoS 原理 · per-port effective policy09 / 22

QoS 的核心是 per-port effective policy，而不是把 Neutron policy 名称直接传给 Rust。

Python translator 先解析 port-level、network-level 和 shared QoS，再按优先级计算每个 port 的最终策略。第一版只支持 bandwidth limit；minimum bandwidth 和 DSCP 不能静默忽略，要进入 unsupported 或 degraded status。

Rust 侧只执行这个最终策略。QoS 失败只影响 QoS domain，不能拖垮 ACL，也不能影响原 OVS 转发。

现有 TCP REST API 可以继续服务 ariactl 和本机管理员，但不能注册 Neutron snapshot route。

apply engine

Apply 顺序要先保证接口存在，再做 durable state，最后推进 generation。

01 schema校验 schema_version、host、mode、authority。
02 preflight确认 binding_host、if_name、ifindex、Netlink。
03 WAL intent写入可恢复 intent，防止半 apply 无法解释。
04 applygroups → conntrack/monitoring → ACL → QoS。
05 commitWAL commit 后再更新 accepted/status。
06 status返回 domain status、last_good、degraded reason。
`accepted_generation` 只能在 WAL durable 且 enhancement 状态可解释后推进。
执行顺序 · generation 语义11 / 22

这一页是 Rust apply engine 的核心约束。不能先把 eBPF map 写了，然后 WAL 失败还说成功。

推荐顺序是先校验 schema 和 authority，再做接口 preflight，然后写 WAL intent，再按 domain apply，最后 WAL commit 和更新 status。

accepted_generation 必须非常保守，只有 durable state 可证明一致、各 enhancement domain 有明确 ready/degraded/bypass 状态后才推进。ACL degraded 不能影响原 OVS 转发。

控制权 · 本机写入保护12 / 22

这是最容易出事故的地方。通信失败不能等价于退出 OpenStack 模式。

只要这个 port 由 Neutron 托管，本机手动改 group、ACL、QoS 或 ACL/QoS config toggle 都要拒绝。trace 可以临时排障，但不能写 WAL，也不能改变 Neutron generation。

如果确实要本机接管，必须显式进入 break-glass，并把本机覆盖写到独立 local-override WAL。恢复时默认 Neutron wins，不做自动 local wins 合并。

multi tenant

多租户不能靠 Rust 侧按 project_id 硬丢包，要靠 Neutron 语义投影。

正确做法

✓

所有对象使用 scoped key：source/project_id/domain/object_id。

✓

Python 侧解析 shared network、RBAC、shared QoS 和显式 ACL scope。

✓

Rust 侧只消费 per-port effective policy，不重新判断 Neutron RBAC。

错误做法

×

看到 project_id 不同就直接丢包，会破坏 shared network 和 router/FIP 路径。

×

用 ACL group 名称或 QoS 名称做 key，会跨租户串 policy。

×

允许 tenant 直接访问 Aria 本机 socket，会绕过 Neutron RBAC。

多租户 · scoped object key13 / 22

多租户适配不能偷懒。最危险的错误是 Rust 侧看到 project_id 不同就 drop，这会直接破坏 shared network、router、floating IP 和 provider network 场景。

正确方式是 Python adapter 读取 Neutron 的 RBAC 和对象关系，然后产出每个 port 的 effective policy。

Rust 侧只需要执行已经解析好的 snapshot。WAL、refcount、pinned map numeric ID 都要从 scoped key 派生或持久化映射。

runtime lifecycle scenarios

VM 迁移、重启、tap 重建，都要靠 Neutron binding + Netlink 对账收敛。

VM create / bind

Neutron event 先到、tap 后出现时，先记录 desired state，返回 `PORT_IFACE_NOT_FOUND`，Netlink NEWLINK 后再 attach。

VM migration

旧 host 看到 binding_host 不再本机就 delete；新 host 等 tap ready 后 port-scoped snapshot。

VM reboot

旧 tap 删除会导致 attach 失效；保留 Neutron desired state，新 ifindex 出现后重新 preflight + attach。

tap 口不存在时不得挂载 eBPF；ifindex 改变时不能复用旧 ifindex runtime。
生命周期 · port / tap / ifindex14 / 22

这页对应真实 OpenStack 环境里最常见的运行时问题。Neutron port 生命周期和 Linux interface 生命周期不是一回事。

迁移时以 binding_host 为准，旧 host 清理，新 host 等 tap 出现再 attach。重启时 binding_host 不变，但 tap 和 ifindex 可能删除重建。

所以 Netlink 监听是必选项。不能只依赖 Neutron RPC，也不能在 tap 还没创建时提前写 accepted state。

安全边界 · bypass/degraded15 / 22

这页是本次方案修正的核心：当前不是 Security Group replacement mode，而是 OVS enhancement mode。

ACL、conntrack、WAL、Netlink 失败都必须清楚上报，但默认结果是 Aria degraded 或 bypass，不能停止原有 OVS 转发。没有配置增强能力是 bypass，配置了但失败才是 degraded。

如果未来要做安全组替代，需要另起显式 replacement mode，再定义独立的中断策略、OVS 过滤链路和回滚方案。

container deployment

容器化交付，但权限必须拆开：datapath 高权限，Neutron adapter 低权限。

aria-datapath container

  • 运行现有 `aria-agent` binary，不改 binary 名。
  • 需要 host network 或等价 namespace。
  • 挂载 `/sys/fs/bpf`、BTF、`/var/lib/aria-agent`、日志目录。
  • 包含 ariactl 和 eBPF artifact。

neutron-aria-agent container

  • Python 容器，接 Neutron RPC/config/heartbeat。
  • 只挂载 `/run/aria` 和 Neutron 配置。
  • 不需要 eBPF capability，不访问 bpffs。
  • 通过 Unix socket 调用 snapshot API。
没有编排平台也可以：两个容器共享宿主机 `/run/aria/aria-agent.sock`。
部署 · 两容器模型16 / 22

之前讨论过是裸机二进制还是容器，最终结论是容器。但容器不是普通隔离应用容器，aria-datapath 仍然是宿主机 datapath runtime。

两个容器不能合并。合并会让 Python adapter 继承 eBPF 特权，安全面扩大，升级和故障定位也复杂。

通信方式参考 OVS agent 和 OVSDB：通过宿主机 Unix socket bind mount，不做 localhost HTTP fallback。

what not to build

这些东西第一阶段明确不做，否则范围会失控。

不做自研 northbound

不让用户绕过 Neutron 创建 OpenStack 网络对象，不开放 tenant 直接调用 Aria。

不做完整 L2 替代

不接管 port binding，不替代 OVS connectivity，不宣称完整 L2 agent。

不搬 v0.10 controller

不迁移 aria-controller，不把 RFC 控制面体系放进这个分支。

不做 TCP 过渡

Neutron snapshot API 只走 Unix socket，不做 localhost HTTP fallback。

不改核心名字

binary 仍是 aria-agent；aria-datapath 只是角色名和容器名。

不接 Mirror / TCPrt

Mirror、TCPrt 以及 trace/drops/ssl/diagnose/service chain 保留代码，但不进 Neutron agent mode API。

不做项 · scope guard19 / 22

这页很重要，因为范围失控通常不是因为大家不知道要做什么，而是因为不清楚什么不做。

第一阶段不做自研 northbound，不做完整 L2 替代，不搬 v0.10 controller，不做 TCP 过渡，不改二进制名字，不接 Mirror/TCPrt，也不把 trace 等本机能力扩成 Neutron 租户功能。

这些约束不是保守，而是为了让第一阶段能交付、能验证、能回滚。

risk register

风险集中在三类：OpenStack 语义、接口生命周期、持久化一致性。

OpenStack 语义风险

  • 误把 Aria ACL enhancement 当成安全组替代链路
  • shared network / shared QoS 误拦截
  • 未启用 ACL enhancement 的端口被误拦截
  • DHCP / metadata / IPv6 ND 被 ACL enhancement 误伤

接口生命周期风险

  • tap 未创建就 attach
  • VM reboot 后 ifindex 改变
  • migration 乱序 event
  • unsupported trunk / SR-IOV 假 ready

状态一致性风险

  • WAL 写失败但 generation 推进
  • pinned map schema 不兼容
  • local override 与 Neutron rejoin 冲突
  • 双容器实例同时写 runtime
每个风险都要变成 status、metric、smoke 或代码 gate，不能只留在文档里。
风险与门槛20 / 22

风险主要分三类。第一类是 OpenStack 语义，比如误把 Aria ACL enhancement 当成安全组替代、shared network、未启用 ACL enhancement 的端口、DHCP 和 metadata 被误伤。

第二类是接口生命周期，比如 tap 还没出现、ifindex 重建、迁移事件乱序、SR-IOV 这种 unsupported port 被误报 ready。

第三类是状态一致性，比如 WAL、pinned map、local override、双实例。所有这些都不能停留在文档里，必须进入 status、metric、smoke 或代码 gate。

before coding into target env

进入真实 OpenStack 前，必须先完成 N0.5 兼容性发现。

必须确认的环境事实

  • OpenStack 版本和 OVS br-int 拓扑。
  • tap 是否直接接入 br-int。
  • 当前没有 Linux bridge、qvo/qvb/veth 和原 SG 过滤链路。
  • Aria degraded/bypass 是否不影响原 OVS 转发。
  • Neutron QoS extension 和 ACL tag/mapping 输入是否可用。

必须确认的内核/容器事实

  • BTF、bpffs、qdisc、TC/XDP attach 能力。
  • `/run/aria`、`/var/lib/aria-agent`、`/sys/fs/bpf` 挂载策略。
  • 双容器无编排部署下的单实例锁。
  • schema/capability 握手和回滚最低兼容版本。
  • unsupported port 类型如何 degraded 或 ignored。
N0.5 · 目标环境发现21 / 22

这页是实际落地前的清单。目标环境固定 OVS，不能只在文档里假设 tap、hook direction 和 bypass 行为。

需要确认 OpenStack 版本、tap 命名、attach 点、原 OVS 转发不被 Aria bypass/degraded 影响，以及 QoS extension 和 ACL tag/mapping 输入是否存在。发现结果必须写入 docs/openstack-target-env-discovery.md。

同时要确认内核和容器能力，尤其 BTF、bpffs、qdisc、XDP/TC attach、host mounts 和单实例锁。
