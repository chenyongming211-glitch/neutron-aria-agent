Aria Firewall
Neutron Agent Mode

在旧版 OpenStack 中把 Aria 做成 Neutron 可管理的 ACL/QoS/Mirror 执行后端：ACL 独立扩展，QoS 对外叫 aria-qos 且复用原生模型，Mirror 第二阶段新增 aria_mirror。

结论：方案可行，优先落 ACL 产品化闭环；aria-qos 作为产品入口复用 Neutron QoS API/DB；Mirror 作为第二阶段独立扩展接入 Aria eBPF clone 能力。

Aria Firewall · v0.9-neutron-agent01 / 26

开场先讲结论。现在方案已经从早期 agent mode 收敛到产品化 Neutron 扩展：ACL 自建 Aria extension，QoS 复用 Neutron QoS。

OpenStack 用户仍通过 Neutron、Horizon、平台后端或 Legacy neutron CLI 配置网络能力；Aria 在 compute node 上作为执行面。

第一阶段只接管普通虚机 OVS tap port。SR-IOV、LinuxBridge、DHCP/router/metadata 等 Neutron 服务端口不纳入 enforcement。

executive summary

最终方案：aria-acl / aria-qos / aria-mirror 三个产品入口统一。

ACL 主线

开发 `aria_acl` service plugin、独立 API/DB/RBAC/RPC、Legacy neutron CLI 和 port-show 只读摘要。

QoS 路线

对外使用 `aria-qos-*`；底层仍启用 Neutron QoS policy/rule/binding，由 Aria 执行。

Mirror 二阶段

不复用现有 `networking_mirror` 语义，新增 `aria_mirror`，支持 global mirror 和按 IP prefix 分流。

判断标准：Neutron 是唯一 source of truth；Aria 是 compute node 上可审计、可降级、可恢复的 ACL/QoS/Mirror runtime。
开发汇报 · 结论页02 / 26

这一页是给管理层和开发团队对齐用的。ACL 不走 Security Group，也不靠 tag/mapping 作为产品形态，而是做独立 Neutron 扩展。

QoS 则相反，不重新设计底层模型。Neutron 里已有 QoS 代码，现场只是未启用；产品入口统一叫 aria-qos，底层仍写原生 QoS。

边界要收紧：Aria 不改 binding:vif_type，不替代 OVS L2，不接管 SR-IOV 第一阶段，也不能误伤 DHCP/router/metadata 端口。

架构 · 两容器边界05 / 26

目标架构分两层。Neutron Server 提供 Aria ACL 的 northbound API、DB 和 RBAC；QoS 仍走 Neutron 原生 QoS policy/rule。

compute 节点新增 neutron-aria-agent。它不替代 OVS agent，只读取 Neutron 状态、发现本 host 的 VM tap、生成 per-port snapshot。

aria-agent 不访问 Neutron DB，也不判断租户权限。它只接收 UDS snapshot，在 tap/采集口上执行 eBPF ACL/QoS/Mirror。

component boundaries

三个边界必须守住：Neutron 管语义，Python 管投影，Rust 管执行。

Neutron Server

  • Aria ACL API/DB/RBAC
  • QoS policy/rule/binding
  • project / port / network
  • agent heartbeat

neutron-aria-agent

  • Python2 兼容
  • 只处理本 host VM OVS tap
  • 翻译 ACL / QoS snapshot
  • full resync + event merge

aria-agent

  • Rust runtime
  • 不访问 Neutron DB/API
  • eBPF attach/map apply
  • WAL / Netlink / runtime status
Rust 侧不解释 Neutron 内部语义；Python 侧不直接操作 eBPF map。
职责边界06 / 26

这页是后面代码 review 的基本边界。Neutron 负责用户语义，Python adapter 负责投影，Rust datapath 负责执行。

Rust 不应该知道 Neutron DB 内部结构，也不消费 Neutron RPC；否则后面版本兼容会很痛苦。

Python 也不应该直接写 eBPF map，它只生成声明式 snapshot。这样失败恢复、幂等、WAL 和 status 才能统一。

acl implementation principle

ACL 是 Aria 独立 Neutron 扩展，不复用 Security Group。

01 APILegacy CLI / 平台调用 Neutron 创建 policy、rule、address-set。
02 DBneutron-server 写 `aria_acl_*` 表，生成 revision。
03 bindingpolicy 绑定到 network 或 port，不写入原生 ports 表。
04 eventRPC notification 或 full resync 触发 agent 重算。
05 tapagent 用 OVS `external_ids:iface-id` 找本机 VM tap。
06 applyUDS 下发 snapshot，aria-agent 写 eBPF map。

API 对象

`aria_acl_policy`、`aria_acl_rule`、`aria_acl_address_set`、`aria_acl_binding`，由 Neutron Server 统一鉴权和审计。

port-show 表达

port 上只展示只读摘要：`aria_acl_enabled`、`effective_policy_id`、`runtime_status`，不改变 `binding:vif_type=ovs`。

ACL 原理 · 显式增强08 / 26

这页讲 ACL 的业务流程。管理员或者平台通过 Neutron API 创建 Aria ACL 对象，Neutron Server 写独立 DB，不复用安全组表。

绑定关系通过 `aria_acl_bindings` 表表达。绑定到 network 时也只展开到 eligible VM ports，不展开到 DHCP/router/metadata 服务端口。

agent 只消费 Neutron 状态并生成 snapshot，aria-agent 只执行 snapshot。这样 ACL 有审计、有回滚、有 runtime status。

qos implementation principle

QoS 对外叫 aria-qos，底层复用 Neutron QoS，执行后端切到 Aria。

Neutron 侧开发

1

启用 `service_plugins += qos,aria_qos`，让 `qos` 和 `aria-qos` 都可见。

2

启用 ML2 `extension_drivers = qos`，保留原生 `qos_policy_id`。

3

`aria-qos-*` CLI 作为 facade，底层调用原生 QoS API。

4

不使用 `qhqos`；它是 Floating IP / Router QoS 定制路径。

Aria 执行规则

✓

neutron-aria-agent 计算 port-level > network-level effective QoS。

✓

aria-agent 写 eBPF QoS map，带 status 和统计。

✓

OVS agent 保持 `extensions = mirror`，不启用 `qos` execution。

✓

tc/shaping 不满足时进入 degraded/unsupported，不宣称 ready。

开发后现象：`aria-qos` extension 可见；`neutron aria-qos-*` 可创建/绑定策略；底层 `qos_policy_id` 生效；Aria 显示 per-port runtime status。
QoS 原理 · per-port effective policy09 / 26

QoS 和 ACL 的策略不一样。ACL 是新产品语义，所以新增 Aria ACL API；QoS 是 Neutron 已有成熟模型，所以底层复用，但产品入口统一叫 aria-qos。

现场镜像里已有 QoS plugin 和 ML2 extension 代码，只是未启用。qhqos 也存在，但它是 Floating IP / router 网关限速，不进入 Aria QoS 路线。

不要启用 OVS agent qos execution，避免同一个 port 被 OVS QoS 和 Aria QoS 双重限速。

apply engine

Apply 顺序要先保证接口存在，再做 durable state，最后推进 generation。

01 schema校验 schema_version、host、mode、authority。
02 preflight确认 binding_host、if_name、ifindex、Netlink。
03 WAL intent写入可恢复 intent，防止半 apply 无法解释。
04 applygroups → conntrack/monitoring → ACL → QoS。
05 commitWAL commit 后再更新 accepted/status。
06 status返回 domain status、last_good、degraded reason。
`accepted_generation` 只能在 WAL durable 且 enhancement 状态可解释后推进。
执行顺序 · generation 语义11 / 26

这一页是 Rust apply engine 的核心约束。不能先把 eBPF map 写了，然后 WAL 失败还说成功。

推荐顺序是先校验 schema 和 authority，再做接口 preflight，然后写 WAL intent，再按 domain apply，最后 WAL commit 和更新 status。

accepted_generation 必须非常保守，只有 durable state 可证明一致、各 enhancement domain 有明确 ready/degraded/bypass 状态后才推进。ACL degraded 不能影响原 OVS 转发。

控制权 · 本机写入保护12 / 26

这是最容易出事故的地方。通信失败不能等价于退出 OpenStack 模式。

只要这个 port 由 Neutron 托管，本机手动改 group、ACL、QoS、Mirror 或对应 config toggle 都要拒绝。trace 可以临时排障，但不能写 WAL，也不能改变 Neutron generation。

如果确实要本机接管，必须显式进入 break-glass，并把本机覆盖写到独立 local-override WAL。恢复时默认 Neutron wins，不做自动 local wins 合并。

multi tenant

多租户不能靠 Rust 侧按 project_id 硬丢包，要靠 Neutron 语义投影。

正确做法

✓

所有对象使用 scoped key：source/project_id/domain/object_id。

✓

Python 侧解析 shared network、RBAC、shared QoS 和显式 ACL scope。

✓

Rust 侧只消费 per-port effective policy，不重新判断 Neutron RBAC。

错误做法

×

看到 project_id 不同就直接丢包，会破坏 shared network 和 router/FIP 路径。

×

用 ACL group 名称或 QoS 名称做 key，会跨租户串 policy。

×

允许 tenant 直接访问 Aria 本机 socket，会绕过 Neutron RBAC。

多租户 · scoped object key13 / 26

多租户适配不能偷懒。最危险的错误是 Rust 侧看到 project_id 不同就 drop，这会直接破坏 shared network、router、floating IP 和 provider network 场景。

正确方式是 Python adapter 读取 Neutron 的 RBAC 和对象关系，然后产出每个 port 的 effective policy。

Rust 侧只需要执行已经解析好的 snapshot。WAL、refcount、pinned map numeric ID 都要从 scoped key 派生或持久化映射。

runtime lifecycle scenarios

VM 迁移、重启、tap 重建，都要靠 Neutron binding + Netlink 对账收敛。

VM create / bind

Neutron event 先到、tap 后出现时，先记录 desired state，返回 `PORT_IFACE_NOT_FOUND`，Netlink NEWLINK 后再 attach。

VM migration

旧 host 看到 binding_host 不再本机就 delete；新 host 等 tap ready 后 port-scoped snapshot。

VM reboot

旧 tap 删除会导致 attach 失效；保留 Neutron desired state，新 ifindex 出现后重新 preflight + attach。

tap 口不存在时不得挂载 eBPF；ifindex 改变时不能复用旧 ifindex runtime。
生命周期 · port / tap / ifindex14 / 26

这页对应真实 OpenStack 环境里最常见的运行时问题。Neutron port 生命周期和 Linux interface 生命周期不是一回事。

迁移时以 binding_host 为准，旧 host 清理，新 host 等 tap 出现再 attach。重启时 binding_host 不变，但 tap 和 ifindex 可能删除重建。

所以 Netlink 监听是必选项。不能只依赖 Neutron RPC，也不能在 tap 还没创建时提前写 accepted state。

安全边界 · bypass/degraded15 / 26

这页是本次方案修正的核心：当前不是 Security Group replacement mode，而是 OVS enhancement mode。

ACL、conntrack、WAL、Netlink 失败都必须清楚上报，但默认结果是 Aria degraded 或 bypass，不能停止原有 OVS 转发。没有配置增强能力是 bypass，配置了但失败才是 degraded。

如果未来要做安全组替代，需要另起显式 replacement mode，再定义独立的中断策略、OVS 过滤链路和回滚方案。

container deployment

容器化交付，但权限必须拆开：datapath 高权限，Neutron adapter 低权限。

aria-datapath container

  • 运行现有 `aria-agent` binary，不改 binary 名。
  • 需要 host network 或等价 namespace。
  • 挂载 `/sys/fs/bpf`、BTF、`/var/lib/aria-agent`、日志目录。
  • 包含 ariactl 和 eBPF artifact。

neutron-aria-agent container

  • Python 容器，接 Neutron RPC/config/heartbeat。
  • 只挂载 `/run/aria` 和 Neutron 配置。
  • 不需要 eBPF capability，不访问 bpffs。
  • 通过 Unix socket 调用 snapshot API。
没有编排平台也可以：两个容器共享宿主机 `/run/aria/aria-agent.sock`。
部署 · 两容器模型16 / 26

之前讨论过是裸机二进制还是容器，最终结论是容器。但容器不是普通隔离应用容器，aria-datapath 仍然是宿主机 datapath runtime。

两个容器不能合并。合并会让 Python adapter 继承 eBPF 特权，安全面扩大，升级和故障定位也复杂。

通信方式参考 OVS agent 和 OVSDB：通过宿主机 Unix socket bind mount，不做 localhost HTTP fallback。

这页是开发路线。ACL 控制面和 datapath 要拆开，先让 Neutron API/DB/CLI 可用，再打开真实 enforcement。

QoS 放在 ACL 之后，因为现场 QoS plugin 未启用，且 tc/shaping 条件还要补齐。Mirror 作为第二阶段增强，新增 aria_mirror，不复用现有 networking_mirror 的 port_id/vm_type 语义。

产品化阶段要把 Kolla 镜像、三节点 smoke、回滚、日志和 metrics 都补齐，不只是功能验证。

what not to build

这些东西第一阶段明确不做，否则范围会失控。

不复用安全组

不消费 `security_group_ids`、remote group、port security，也不做默认安全组自动绑定。

不改 VIF 类型

`binding:vif_type` 仍然是 `ovs`，Aria 不是新的 Nova/libvirt plug 类型。

不接管 SR-IOV

SR-IOV direct / direct-physical 第一阶段标记 unsupported，需要后续独立 backend。

不接管服务端口

`network:dhcp`、router、metadata 等 Neutron 服务端口显示 not_applicable，不进 ACL snapshot。

不启用 OVS QoS 执行

Aria QoS 路线下 OVS agent 保持 `extensions = mirror`，避免双重限速。

不开放本机租户 API

租户和平台只能走 Neutron API/CLI，不能直接调用 aria-agent socket 绕过 RBAC。

不做项 · scope guard19 / 26

这页很重要，因为范围失控通常不是因为大家不知道要做什么，而是因为不清楚什么不做。

第一阶段不走安全组替代链路，不改 VM plug 方式，不接管 SR-IOV，不接管 DHCP/router/metadata 服务端口，不启用 OVS agent QoS 执行。

这些约束不是保守，而是为了让第一阶段能交付、能验证、能回滚。

risk register

风险集中在三类：OpenStack 语义、接口生命周期、持久化一致性。

OpenStack 语义风险

  • 误把 Aria ACL enhancement 当成安全组替代链路
  • shared network / shared QoS 误拦截
  • 未启用 ACL enhancement 的端口被误拦截
  • DHCP / metadata / IPv6 ND 被 ACL enhancement 误伤

接口生命周期风险

  • tap 未创建就 attach
  • VM reboot 后 ifindex 改变
  • migration 乱序 event
  • unsupported trunk / SR-IOV 假 ready

状态一致性风险

  • WAL 写失败但 generation 推进
  • pinned map schema 不兼容
  • local override 与 Neutron rejoin 冲突
  • 双容器实例同时写 runtime
每个风险都要变成 status、metric、smoke 或代码 gate，不能只留在文档里。
风险与门槛20 / 26

风险主要分三类。第一类是 OpenStack 语义，比如误把 Aria ACL enhancement 当成安全组替代、shared network、未启用 ACL enhancement 的端口、DHCP 和 metadata 被误伤。

第二类是接口生命周期，比如 tap 还没出现、ifindex 重建、迁移事件乱序、SR-IOV 这种 unsupported port 被误报 ready。

第三类是状态一致性，比如 WAL、pinned map、local override、双实例。所有这些都不能停留在文档里，必须进入 status、metric、smoke 或代码 gate。

Mirror 二阶段 · 语义对比22 / 26

这一页先避免概念混淆。现有 networking_mirror 的 port_id 从代码看是目标分析 VM port，不是被镜像的源 port。

现有实现依赖 br-mirror、patch port、br-int group 10 和 table 100/101/102。Aria mirror 则是 eBPF clone 到 target ifindex。

因此建议保留现有 mirror，不改它的语义；第二阶段新增 aria_mirror，字段明确拆分 source 和 target。

Mirror 二阶段 · global + policy23 / 26

这里补进用户明确提出的两个需求：全局镜像和按不同 IP 网段分流到不同 VM port。

全局镜像直接复用 Aria 当前已有的 global mirror 能力。policy mirror 用 rule 表达匹配条件，rule 级 target_port_id 允许不同 prefix 去不同分析 VM。

冲突规则也要说清：同一 source 和 direction 下 rule 必须有 priority，同优先级 prefix 重叠第一版建议直接拒绝。

aria_mirror development plan

开发拆成四层：API/DB、CLI、translator、Aria-agent contract。

1. Neutron API/DB

  • `aria-mirror` extension alias
  • `aria_mirror_sessions` / `rules` / `statuses`
  • `mirror_mode=global|policy`
  • rule 级 target override 和 priority validator

2. Legacy CLI

  • `neutron aria-mirror-session-*`
  • `neutron aria-mirror-rule-*`
  • `neutron aria-mirror-status-show`
  • host interface source 只允许 admin

3. neutron-aria-agent

  • full resync + 增量事件
  • source/target OVS tap discovery
  • prefix/address-set 编译成 group
  • cross-host / unsupported 状态上报

4. aria-agent

  • OpenStack snapshot mirror domain
  • `MIRROR_GLOBAL` / `MIRROR_POLICY` 下发
  • mirror stats 回传
  • 失败只影响 mirror，不阻断原业务流
开发后现象：`neutron ext-show aria-mirror` 可见；能创建全局镜像和 prefix 分流镜像；status 能展示 source/target ifindex、packets、bytes、errors。
Mirror 二阶段 · 开发拆分24 / 26

这一页是开发任务拆分。Neutron Server 先提供 API/DB 和 validator，CLI 给旧环境运维入口，Python agent 负责翻译，Rust agent 负责执行。

这页讲验收。最重要的不是只看到包到了，而是状态能解释、失败不影响原始业务流、删除后 map 清理。
