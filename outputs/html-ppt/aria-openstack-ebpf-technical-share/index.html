positioning

Aria 是 OpenStack/OVS-aware eBPF 数据面增强平台

它是什么

Aria 在普通虚机 OVS tap 口上提供 ACL、QoS、Mirror 和可观测增强能力。

控制面走 Neutron，数据面由本机 aria-datapath 通过 eBPF 执行。

它不是什么

  • 不是 OVS 替代品。
  • 不是 Security Group 的改名实现。
  • 不是绕过 Neutron 的独立租户控制面。
  • 不是直接接管所有网卡类型的万能 agent。
一句话：Neutron 负责产品入口，OVS 负责基础转发，Aria 负责本机 tap 侧 eBPF 增强执行和状态反馈。

background and goals

目标不是重写 OpenStack 网络，而是补一条可产品化的数据面增强路径

现有路径

普通 VM port 在计算节点上表现为 tap 设备，接入 OVS br-int。原生能力通常依赖 OVS flow、iptables、tc 或 agent extension。

Aria 路径

Aria 不改变 Neutron port 绑定和 OVS L2 转发，只在明确声明的本机接口上增加 eBPF 增强执行。

失败原则

失败时进入 degraded/bypass，状态必须可见，优先保护 OVS 原业务转发，不因为 Aria 异常主动打断基础链路。

目标能力：统一入口、清晰边界、可恢复事务、可观测运行状态、按 domain 渐进扩展。

acl semantics

ACL 语义：显式绑定才生效，状态必须可解释

对象模型

  • policy：策略容器。
  • rule：匹配条件和 action。
  • address-set：IP/CIDR 集合。
  • binding：绑定到 port 或 network。
  • port-status：运行时状态读回。

执行原则

  • 未绑定策略不改变流量。
  • 端口不支持时状态要可见。
  • 下发失败时不能假装 ready。
  • 状态要说明 host、generation、effective_action 和原因。
方向以 VM tap 视角定义：ingress 是进入 VM tap，egress 是 VM tap 发出。

snapshot

snapshot 是“本机期望状态快照”，不是虚机磁盘快照

它包含什么

  • 当前 host 上有哪些 Neutron ports。
  • 哪些 port 是 eligible OVS tap。
  • 每个 port 被哪些 domain 托管。
  • 每个 port 应该应用哪些 ACL/QoS/Mirror 策略。
  • generation、desired_hash、host、ifname 等收敛信息。

为什么需要它

  • datapath 不直接读 Neutron DB。
  • 复杂 Neutron 对象先被 agent 翻译成本机可执行目标状态。
  • 同一个 snapshot 可以重复下发，保证幂等。
  • 重启、恢复、纠偏时可以重新下发。

snapshot example

snapshot 把 Neutron 逻辑策略变成本机可执行说明书

transaction and recovery

事务模型：最终一致、可恢复、可审计

stateDiagram-v2
  [*] --> DesiredBuilt: 生成 desired snapshot
  DesiredBuilt --> Prepared: prepare generation / desired_hash
  Prepared --> Submitted: UDS 提交
  Submitted --> Intent: WAL intent
  Intent --> Preflight: host / ifname / ifindex 校验
  Preflight --> Applying: attach / map apply
  Applying --> Committed: WAL commit + status hash
  Committed --> Ready: ready / enforce

  Preflight --> Degraded: 校验失败
  Applying --> Degraded: apply 失败或中断
  Degraded --> Bypass: 保护 OVS 原转发
  Bypass --> Resync: full-resync / replay
  Resync --> Ready: 收敛成功
  Resync --> Blocked: 状态不确定

transaction details

事务不是分布式强 ACID，而是分层保证“不静默、不误报、可恢复”

层次
事务与恢复机制
Neutron Server
CRUD 与 revision 在同一 DB transaction；notification 在 DB commit 后发送。
neutron-aria-agent
generation、desired_hash、pending snapshot/delete、本地状态恢复、full-resync 兜底。
aria-datapath
WAL intent/commit/replay、status hash、preflight、apply lock、rollback。
eBPF runtime
apply 失败进入 degraded/bypass，不能破坏 OVS 原转发，不能假装 ready。

aria-qos

QoS 不重造模型：产品入口叫 Aria QoS，底层复用 Neutron QoS 语义

推荐分层

  • 产品入口：Aria QoS / aria-qos。
  • 底层语义：Neutron QoS policy/rule。
  • 执行后端：Aria datapath。
  • 状态表达：Aria QoS runtime status。

必须先澄清

  • QoS API 是否可见。
  • policy 如何绑定到 port/network。
  • Aria 是否拥有 QoS domain 写权限。
  • 执行路径是 shaping、policing-only，还是 unsupported。
重点是避免 OVS agent QoS、tc、已有定制 QoS 插件与 Aria 形成双重限速。

observability

可观测性是 Aria 的产品差异化方向

Policy API

给 Neutron / 平台控制面使用，用于创建和下发 ACL、QoS、Mirror 策略。

Observability API

给监控、审计、平台 UI 使用，查询 counters、drop reason、rule hit、速率和事件。

Admin API

给运维和支持工具使用，查看 capabilities、WAL、attach、map、rollback、health。

长期价值不是“能拦包”，而是能解释哪个 tenant、VM、port、rule 造成了什么结果。

fail-open contract

最高原则：Aria ACL 是安全增强，不能成为 OVS 转发的单点依赖

最终目标

不管 Aria 控制面、aria-datapath、eBPF attach、map apply、ACL 编译或状态回报发生什么故障，原有 OVS baseline forwarding 都不能被 Aria 主动打断。

最坏结果只能是 ACL enforcement 降级为 bypass，而不是业务流量中断。

产品语义

  • ready + enforce：ACL 明确生效。
  • not_requested + bypass：没有 ACL 绑定，不改变转发。
  • degraded + bypass：ACL 异常，保护 OVS 原业务。
  • unsupported + bypass：端口类型不支持，不接管。
一句话：Aria 可以增强 OVS tap 流量，但不能让 OVS 转发依赖 Aria 正常运行。

mechanism

Fail-open 不是一句口号，而是控制面、事务层和 eBPF 热路径共同保证

1控制面先判定有效性。没有 binding、策略缺失、端口不支持、规则非法时，生成 bypass 状态，而不是生成危险的 drop 规则。
2apply 前先关闭 ACL gate。端口更新时先 acl_enabled=false，清理旧 Neutron ACL，再写新 group/policy，最后才 enable。
3事务只提交收敛状态。WAL intent/commit、generation、desired_hash 保证失败不会被误报成 ready。
4eBPF 默认 PASS。XDP 默认 XDP_PASS，TC 默认 TC_ACT_OK；解析失败、map 缺失、内部异常都走放行。
5只在 ready/enforce 时 drop。只有 ACL gate 打开、规则明确命中 deny/drop 时，eBPF 才能丢包。

hard rules

后续开发必须守住这 6 条硬约束，避免“安全增强”变成“转发风险”

1. Aria runtime 永远不主动重启 OVS、OVS agent、neutron-server。

2. eBPF 入口默认放行；未知状态、解析失败、map miss 不允许默认 drop。

3. ACL 只有 ready + enforce 且 per-port gate 打开时才能丢包。

4. 任何 apply 失败必须进入 degraded + bypass 或保持上一代 committed 状态。

5. 无支持能力的 port 必须显式 unsupported/not_applicable + bypass，不能静默接管。

6. 监控必须区分 ACL enforcement 状态和 OVS forwarding 状态，不能混成一个 pass/fail。

这组约束就是最终产品原则：Aria 可以失效，业务转发不能因为 Aria 失效而中断。

product wording

对业务方可以这样讲

ACLAria 为 OpenStack 普通虚机 OVS tap 端口提供独立 ACL 增强能力；控制面走 Neutron，数据面走本机 eBPF。
QoSAria QoS 的产品入口保持统一命名，底层复用 Neutron QoS 策略语义，后续由 Aria datapath 执行。
MirrorAria Mirror 是面向 Aria 管理接口的独立镜像能力，支持 global_l2 与按 IP/协议/方向的选择性镜像。
失败行为Aria 异常时优先进入 degraded/bypass，不主动破坏 OVS 原有转发；状态通过 heartbeat 和 port status 暴露。

takeaways

最后要让听众记住这几件事

1. Aria 是 OpenStack/OVS-aware eBPF 数据面增强平台，不是 OVS 替代品。

2. Neutron Server 是生产 northbound，Aria 不绕过 Neutron 创建租户策略。

3. ACL 使用独立 aria-acl，不复用 Security Group。

4. QoS 产品入口叫 aria-qos，底层复用 Neutron QoS 语义。

5. Mirror 建议独立 aria-mirror，避免复用已有 mirror API 的语义歧义。

6. 事务模型是最终一致、可恢复、可审计，失败时优先保护原业务转发。

7. SR-IOV legacy/direct 当前只做识别、跳过、状态可见。

8. 后续真正支持 SR-IOV，推荐走 switchdev / VF representor 路线。
